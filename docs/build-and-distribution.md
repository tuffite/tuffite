# Tuffite build and distribution

## 1. Product artifacts

Tuffite separates the expensive Chromium build from application iteration. A
versioned Framework Distribution contains:

```text
Tuffite Framework Distribution
├── tuffite-framework.json (identity, ABI, variant, features, files and SHA-256)
├── lib/ (Framework import libraries for native development)
├── tuffite_launcher executable template (renamed to the business executable at package time)
├── runtime/ (Framework, Chromium helpers and resources)
├── Tuffite Runtime
├── public Rust crates and procedural macros
├── single `tuffite` npm package with renderer runtime and ShellAPI types
├── CLI and build support
├── symbols or symbol-server metadata
├── licenses and Chromium notices
└── signed artifact manifest
```

An application build contains:

```text
Application package
├── business-owned Rust runtime library
├── application-named native sandbox executable
├── version-matched Tuffite Framework runtime library
├── Chromium resources and subprocess runtime dependencies
├── packaged resources under the manifest-defined scheme
├── application manifest and capability policy
├── icons and platform metadata
└── updater/signing metadata
```

Applications do not link against or rebuild Chromium. Framework developers do
build Chromium when changing Framework, FFI, Shell Binding, `<explorer>`, or an
upstream integration hook.

The Framework identity is the tuple of framework version, pinned Chromium
revision, Rust target triple, build profile, component-build mode, variant,
feature set, and FFI ABI. Distributions for different tuples are never treated
as interchangeable. The default discovery order is:

1. `TUFFITE_FRAMEWORK_DIST`, for an explicit developer-managed extracted
   distribution that Tuffite never replaces;
2. `TUFFITE_FRAMEWORK_DIST_DOWNLOAD_DIR`, for an exact Tuffite-managed download
   destination, otherwise `TUFFITE_FRAMEWORK_DIST_CACHE` or the platform user cache under
   `<cache>/tuffite/framework/<framework-version>/<target-triple>`;
3. the version-matched GitHub Release asset, downloaded into that cache.

The default GitHub repository comes from the crate's compile-time Cargo
`repository` metadata. `--repository` and `TUFFITE_GITHUB_REPOSITORY` are
explicit overrides. Private repositories authenticate with `GITHUB_TOKEN`,
`GH_TOKEN`, or the active `gh auth` login.

`tuffite::build::framework::Resolver` exposes the same policy to `build.rs`; new
projects generated by `tuff init` use it by default. Its `.distribution(path)` selects a
developer-managed artifact, `.download_directory(path)` selects an exact
managed destination, `.cache_root(path)` changes the cache root, and
`.auto_download(false)` requires the artifact to be present already. The
equivalent environment switches are `TUFFITE_FRAMEWORK_DIST`,
`TUFFITE_FRAMEWORK_DIST_DOWNLOAD_DIR`, `TUFFITE_FRAMEWORK_DIST_CACHE`, and
`TUFFITE_FRAMEWORK_DIST_AUTO_DOWNLOAD=0`. Repository and release overrides use
`TUFFITE_GITHUB_REPOSITORY` and `TUFFITE_FRAMEWORK_DIST_RELEASE_TAG`.
`TUFFITE_FRAMEWORK_DIST_TARGET` selects an exact Rust target triple.

On Apple Silicon, an implicit `aarch64-apple-darwin` resolution prefers the
native Release asset and falls back to `x86_64-apple-darwin` when only that
artifact is published. The application Rust library is then built for x86_64
as well and the packaged application runs through Rosetta 2. Explicit targets
never fall back; set `TUFFITE_FRAMEWORK_DIST_TARGET=aarch64-apple-darwin` to require a
native ARM64 artifact.

Downloads and uploads report progress by default. Interactive terminals get a
single updating progress bar; upload shows percentage, transferred size, speed,
and remaining time. Captured
or CI output receives throttled byte progress instead of terminal control
sequences. Pass `--no-progress` to
`python3 x.py upload`, set `TUFFITE_FRAMEWORK_DIST_PROGRESS=0`, or call `.progress(false)` on the
resolver to disable it.

`tuff dev --force-download-framework` ignores `TUFFITE_FRAMEWORK_DIST` and any
valid cached Distribution for the initial development-package preparation,
downloads the matching GitHub Release asset again, and atomically replaces the
managed destination. Subsequent source-triggered rebuilds in the same dev
session reuse that freshly verified download.

The public build API has three deliberate layers:

- `tuffite::build::framework::Resolver` resolves or downloads the native artifact;
- `tuffite::build::shell_api::Generator` configures generated bindings and their
  write/verify policy;
- `tuffite::build::Builder` assembles both for an application `build.rs` and
  returns a `BuildOutput` containing the resolved Distribution and generated
  bindings. It also emits Cargo rerun directives for the manifest, ShellAPI
  declaration and verified-output paths, and every Framework environment
  override; application build scripts do not repeat those declarations.

`Generator::new()` reads `tuffite.json` beside `build.rs` using
`CARGO_MANIFEST_DIR`; `.manifest(path)` overrides that convention. `.rust(directory,
mode)` emits `bindings.rs` and its fragments together; `.javascript(directory,
mode)` emits `index.js`, `index.d.ts` and all per-input modules together.
`.cpp(directory, mode)` serves Framework binding generation. No output filename
or extension guessing is needed.

```rust,no_run
use tuffite::build::{Builder, framework::Resolver, shell_api::{Generator, OutputMode}};

fn main() -> Result<(), String> {
    let out = std::env::var_os("OUT_DIR").expect("Cargo OUT_DIR");
    Builder::new()
        .add(Resolver::from_env()?)
        .add(Generator::new()
            .rust(std::path::PathBuf::from(out), OutputMode::Write)
            .javascript("generated", OutputMode::Verify))
        .build()?;
    Ok(())
}
```

Both components are required, in either addition order, and duplicates are
rejected. Framework resolution runs before generation. Source manifests put
namespace, declarations and facade under `build.shellApi`. Packaging removes
`build` and emits only namespace and command IDs under the runtime
`app.shellApi`; capability grants remain under `app.security.capabilities`.

Application crates build a business runtime library without linking Chromium.
`tuff build` still resolves the Distribution so its target triple controls
Cargo and a missing artifact is populated into the cache before later staging.
Packaging installs `tuffite_launcher` under the business executable name.
A framework release job creates, validates, and
publishes the reusable C++ artifact once through the framework CLI:

```console
python3 x.py package --profile release --destination dist/tuffite-framework
python3 x.py verify dist/tuffite-framework
python3 x.py upload --distribution dist/tuffite-framework --create --prerelease
```

The package command uses the internal `scripts/framework.py` module, which alone
invokes GN to snapshot `runtime_deps`. Normal application
builds and `tuff package` consume the manifest and never require a Chromium
checkout, GN, or Ninja. Distribution installation should verify all hashes once; package
assembly checks sizes and hashes the final package to avoid reading a large
runtime twice on every application build. Symbols belong in a separate release
artifact unless explicitly requested.

`full` and `desktop` are distribution identities, not post-copy deletion
shortcuts. The packager may remove symbols, source maps, test data, and graphics
validation layers. Capability-bearing libraries such as WebRTC, WebNN, XR, or
SwiftShader remain until the matching GN targets are disabled and the resulting
runtime closure passes startup and sandbox tests.

The default Windows release profile is non-component and produces one Framework
DLL. Packaging renames the native `tuffite_launcher` template to the business executable
name; it owns Chromium's sandbox and loads the manifest-selected Rust runtime
through the C ABI. Component builds are an explicit `--component` iteration
mode and use a separate output directory. Artifacts from the two modes must
never mix.

## 2. Developer workflow

The intended workflow is:

```console
tuffite new demo
cd demo
tuff dev
tuff build
tuff package
```

`tuff dev` refreshes an unpacked application package and launches it
against the loopback HTTP development URL declared in the source
`tuffite.json`. It owns the Vite
process in a kill-on-drop process tree, waits up to 30 seconds for an
authenticated readiness response, and terminates that tree when the application
exits or the CLI unwinds. `build.devPackage`, `build.devUrl`,
and `build.beforeDevCommand` provide application defaults; explicit CLI options
override them without trusting an unrelated process that happened to occupy the
configured port. For example:

```console
cargo tuff dev
```

The Framework Distribution is prepared once. On each invocation, `tuff dev`
builds the Rust application cdylib and refreshes the unpacked development
package without generating a ZIP. Subsequent Web edits flow through normal Vite
HMR without rebuilding or repackaging Chromium or Rust. `--tuffite-dev-url` is an internal launch switch and is
unusable alone:
the CLI creates a per-run 256-bit nonce, verifies its digest through the Vite
probe, and passes the digest plus the nonce through separate inherited channels.
The Framework accepts only a valid pair from its direct CLI parent. Tuffite also
accepts only credential-free HTTP loopback URLs, replaces only the primary
startup URL, and grants only that exact origin temporary ShellAPI, Explorer-owner,
and window-navigation access. The default `release.gn` keeps this authenticated
path for local development; CI builds compile it out. Normal production launches
have no CLI-issued nonce and therefore cannot activate the override. The packaged
`tuffite.json`, application scheme,
resource root, and production archives are unchanged. Applications should use
the `tuffite/vite` plugin so `/tuffite-runtime.js`,
`/tuffite-shell-api.js`, the generated application facade, and optional local
preview assets are available from the development origin.

### Current Playground workflow

The Framework provides the Python 3 `x.py` entry for checkout maintenance,
and `spo` for Git patch stacks. Bootstrap the outer workspace with
`mise run setup`; gclient performs the initial checkout. After switching a local
Framework branch, run `python3 x.py roll` from `src/tuffite` to sync dependencies and
apply that branch's patches while preserving the Framework branch. See
[Developer workflow](development.md) for roll recovery and CI options.
macOS native builds require full Xcode.

The common commands are:

```console
python3 x.py roll
python3 x.py build --run
cargo spo
```

Release is the default profile and `src/out/TuffiteRelease` is its persistent
Chromium output. Application commands `tuff build`, `tuff package`, and
`tuff dev` materialize checked-in JavaScript and TypeScript bindings from
`tuffite.json` before compiling or packaging.

Native iteration and distribution publication use:

```console
python3 x.py build --framework
python3 x.py package --skip-build --destination dist/tuffite-framework
python3 x.py verify dist/tuffite-framework
python3 x.py upload --distribution dist/tuffite-framework --replace
cargo run --package tuffite --bin tuff -- package --manifest playground/tuffite.json
python3 x.py test --suite smoke
```

`python3 x.py` invokes its internal Python 3 GN/Ninja backend.
The implicit configure step compares `args.gn` by content. It
run `gn gen --check` only when the output is new or its selected preset changed.
Normal `BUILD.gn` and `.gni` edits are regenerated by Ninja itself. Native
builds request the single `distribution` boundary, which includes the
native sandbox bootstrap and selected runtime linkage, and reuse both the Ninja
output and sccache. ABI layout assertions compile as part of the real bridge
instead of a separate test-only executable. Distribution creation is intentionally
outside the fast `build` loop because hashing and copying a component runtime
of this size is not application compilation.
Ninja defaults to two thirds of available logical CPUs, rounded down with a minimum of one;
use `--jobs N` to override it for a specific build. The local release preset
allows two concurrent links for faster iteration; other profiles keep large
links serialized to cap peak memory.
Run `python3 x.py compdb` after changing GN sources. It writes a focused
`src/tuffite/compile_commands.json`, which VS Code clangd
discovers through `tuffite.code-workspace`. The workspace also disables the
Microsoft C/C++ IntelliSense engine to avoid duplicate diagnostics and provides
tasks for focused and full compilation databases. Use the full task, or
`python3 x.py compdb --all`, only when indexing the whole Chromium checkout is
intentional.
On Windows, concurrent Cargo processes must not share one `CARGO_TARGET_DIR`;
run them sequentially or assign separate directories to avoid incremental-cache
file locking.
If a renamed header leaves an old path in a cache-restored Ninja depfile, use
`ninja -d explain` to confirm it and set `SCCACHE_RECACHE=1` for one rebuild. A
full output-directory deletion is unnecessary.

Choose native presets explicitly with `--profile debug`, `--profile ci`, or
`--profile component`. Build specific targets with
`python3 x.py build --framework --target base:base_unittests`. Component artifacts use
a profile-qualified Distribution directory.

The public `tuffite` CLI serves application developers. `python3 x.py` serves Framework
developers. Shared Distribution APIs live in `tuffite::build::framework`.
`cargo spo` manages Git commits and checked-in patch mailboxes. Mise provides
pinned tools; gclient synchronizes dependencies under `python3 x.py roll`.

Packaging itself is implemented by the cross-platform `tuffite` Rust binary,
enabled by the public crate's default `cli` feature. Applications disable
default features to keep runtime dependencies small. The CLI uses `clap` derive for cross-platform
subcommands, help text, required arguments, and validation. With a prebuilt
distribution it reads the frozen runtime file list and renderer resources from
`bundle.resources`, writes a deterministic per-file SHA-256 manifest, and
creates the selected directory, archive, or native bundle. It rejects absolute, parent-relative,
and symbolic-link resource paths. The CLI injects the version-matched renderer
runtime and generated built-in ShellAPI facade from the single `tuffite` npm
package; applications cannot shadow those reserved framework resources. A
direct invocation is:

Application assets are explicit `app.assets[]` origin/path rules. Each rule
maps paths to one project-relative `file` or `directory`; the packager includes
those sources automatically alongside `bundle.resources`. Exact paths take
priority over prefix paths, and ambiguous equal-priority mappings fail validation.
SPA routes explicitly map to their index file; no `frontend` or generated
`assetRoutes` index is used. See the
[complete configuration example](../components/explorer/README.md#manifest).
`app.security.csp` sets the response policy for packaged assets.

```console
cargo run --package tuffite --bin tuff -- package --manifest playground/tuffite.json --destination dist --name tuffite-playground-windows-x64 --force
```

`tuff package` resolves the Cargo package beside `tuffite.json`, builds its
single library target containing the `cdylib` crate type in release mode, and
obtains the actual artifact path from Cargo's JSON messages.
`bundle.executable` optionally overrides the
installed executable stem; otherwise the Cargo package name is used.
`cargo run --package tuffite --bin tuff -- package --manifest playground/tuffite.json` uses the application packager and resolves the Framework from
`TUFFITE_FRAMEWORK_DIR` or an explicit `TUFFITE_FRAMEWORK_DIST`. Prepare the local
Distribution with `python3 x.py package` first. The
business executable is the package entrypoint. Downstream applications consume
the Rust CLI and a prebuilt Framework Distribution; they do not need the native build backend.

The smoke test verifies binary ShellAPI, a sandboxed application utility
service, a browser-process Network Service request, the full
`current/setTitle/create/list/close` window lifecycle, and `<explorer>`
rendering.
Explorer success requires a screenshot of
the element region from the outer composited Surface; `loadstop` alone is not
considered success.
On Windows, `run-tuffite.cmd` also grants the extracted package directory the
read/execute ACL required by Chromium AppContainer subprocesses before launch.
Packaging strips copied macOS/Linux native images by default, without changing
the original build. Use `--no-strip` to preserve runtime debug information.
`--symbols-dir dist/symbols` exports matching private application symbols before
stripping. Framework symbols are exported separately by `x.py package`; retain
both artifacts for crash diagnostics. `--include-symbols` includes external symbol
sidecars in the runtime and is usually unnecessary for a public package.

`--format zip` is the default. `directory` writes only the unpacked package;
macOS `app` writes a Finder application bundle and `dmg` writes that bundle plus
a compressed disk image with an Applications link. Windows `exe` writes the
runtime directory plus a per-user NSIS installer. The CLI provisions NSIS automatically.
Installer formats require the matching host; macOS `.pkg` is deferred.

```sh
tuff package --format app
tuff package --format dmg --symbols-dir dist/symbols
tuff package --format exe
```

Application commands (`check`, `build`, `doctor`, `dev`, and `package`) search
from the current working directory up through its parents for the nearest
`tuffite.json`. Pass `--manifest path/to/tuffite.json` to override discovery.
`check`, `build`, and `doctor` also retain their positional manifest argument.
The default package output is `<project>/dist`; an explicit `--destination`
is relative to the current working directory.

Set the optional top-level `productName` for the application display name. It
defaults to the Cargo package name and supports spaces and Unicode using portable
filename characters (up to 128 UTF-8 bytes). It names the default `.app` bundle,
macOS display metadata, DMG volume, and Windows installer/shortcut display.
`bundle.executable` controls the executable independently, and `--name` overrides
output names. Application identifiers continue to identify installations.

Neither source nor packaged application `tuffite.json` contains `schemaVersion`. `$schema` remains optional editor metadata.

macOS bundles contain code in `Contents/MacOS`, resources in
`Contents/Resources`, and an ad-hoc signature. Bundle manifest file paths are
relative to `Contents`; the main executable is covered by codesign rather than
a circular self-hash. Developer ID signing and notarization are separate release
steps. Flat packages retain SHA-256 for every runtime file.

Unconfigured icons use the Tuffite logo. Override native icons with safe,
project-relative paths in `tuffite.json`:

```json
{"bundle":{"icons":{"macos":"icons/app.icns","windows":"icons/app.ico"}}}
```

The macOS icon is referenced by `Info.plist`. The Windows icon is embedded in
the executable and used by the installer and Start Menu shortcut.

The current Windows x64 Playground output locations are:

```text
dist/tuffite-playground-windows-x64/
dist/tuffite-playground-windows-x64.zip
```

The flat directory contains `manifest.json` with a SHA-256 and size for every
packaged runtime file. The ZIP contains the directory as its single package
root, so it can be extracted without mixing files into the destination.
The separate `tuffite.json` is the runtime application manifest; it is parsed
and version-checked before browser-process application startup.

Application assets always live under the framework-owned `assets` package
directory. Applications discover that location through `tuffite.path` instead
of configuring a filesystem path in the manifest.

`app.windows` declares one or more startup windows. Labels are unique, stable
application identifiers and are returned in `WindowInfo`; the first window is
the primary application surface. A window may set `decorations: false` to use
application-drawn chrome and Chromium CSS draggable regions while preserving
native resize/minimize/maximize/close behavior; decorations default to `true`.
`bundle` contains distribution-only inputs
and is not a runtime capability namespace. `bundle.executable` is an optional
extension-free executable stem; when omitted it defaults to the Cargo package
name. The runtime library name comes from the package's single cdylib target.
`build` is source-tooling configuration consumed by `tuff dev`; the
browser process does not treat it as a capability grant. Relative package and
working-directory paths are resolved from `tuffite.json`. CLI options override
these defaults for one run. `beforeDevCommand` may be a shell script string or
an object with `script` and `cwd`. An optional `devtoolsPort` enables the loopback-only
CDP endpoint for that development launch; `--devtools-port` overrides it. The CLI
checks availability before starting and prints both the JSON target list and the
browser inspect page. Production launches do not consume this setting.

The selected Framework Distribution also selects the native Cargo target. Tuffite
passes its manifest target to `cargo build --target`, so an arm64 development
host can build an x86_64 application runtime for an x86_64 Framework. Package
platform and architecture metadata come from that same target.

`"tuffite.devtools.inspectElement"` in `shellApi` in a matching origin capability opts trusted root App surfaces
into Tuffite's browser-owned context menu and its **Inspect element** command.
The capability defaults to `false`. Invoking the command starts a loopback
DevTools server on an ephemeral port for the local frontend; it does not expose
the fixed development CDP port configured by `build.devtoolsPort`.
Explorer surfaces continue to use the independent, mutable
`contextMenuEnabled` property.

Explorer is compiled into Tuffite but native permissions default to deny.
`app.security.capabilities[].explorer` authorizes owner creation and scripts.
Guest ShellAPI grants depend on the guest's own
committed origin and are rechecked on every invocation.

The repository keeps three independent Chromium outputs:

| Profile     | GN preset / output                 | Optimization and diagnostics                              |
| ----------- | ---------------------------------- | --------------------------------------------------------- |
| `debug`     | `debug.gn` / `TuffiteExe`           | Non-component, full symbols, no ThinLTO                   |
| `release`   | `release.gn` / `TuffiteRelease`     | Default non-component, size optimization, symbol level 1  |
| `component` | `component.gn` / `TuffiteComponent` | Explicit component mode for faster native iteration       |
| `ci`        | `ci.gn` / `TuffiteCI`               | Non-component, zero symbols, no cache wrapper requirement |

Use `cargo run --package tuffite --bin tuff -- package --manifest playground/tuffite.json` for local package iteration and
`python3 x.py package --profile ci --non-interactive` for CI artifacts. These profiles do
not yet imply production readiness. `is_official_build` remains false: enabling
it is not a substitute for eliminating test-only dependencies and provisioning
Chromium's official-build inputs. Local symbol level 1 supports stack and line
diagnosis; use `debug` for local variables and full type information.

Rust `release` uses optimization level 2, line tables, and incremental-friendly
codegen settings. The custom `ci` profile uses size optimization and
single-codegen-unit output
while retaining ordinary COFF interoperability. Both preserve unwinding for
FFI panic containment.
`--include-symbols` only includes existing symbols; it cannot recreate symbols
removed by the CI build. Use a local release/debug build for diagnostic packages.
Direct `cargo build --profile ci -p playground` builds only the business runtime
library; native executable artifacts are composed at package time.

`python3 x.py test --suite framework` runs Rust checks and browser runtime tests without a Chromium
output. Build the Playground task separately to validate the application against
a built Framework. Both debug and optimized builds generate/check the GN graph on first
use. `CARGO_TARGET_DIR` is respected; otherwise artifacts stay in this checkout's
`target/`, avoiding collisions between different checkouts.

The production Framework owns its browser client, BrowserContext, native window
host, and `tuffite.pak`; it does not link Content Shell. On Windows, the native
host statically links Chromium's sandbox broker because Chromium rejects sandbox
launches initiated solely from a DLL. The distribution/package
runtime policy removes source maps, test fonts/data, Python build helpers,
graphics mock/validation layers, `.pak.info`, and symbols. It preserves
`tuffite.pak`, `tuffite_locales/en-US.pak`, ICU and V8 snapshots, Crashpad,
ANGLE, SwiftShader, and other production runtime files.

### Runtime size policy

The normal Windows `desktop` distribution is approximately 1.07 GiB unpacked
because a Chromium component build emits hundreds of runtime DLLs. The largest
15 files account for roughly 53% of the runtime and the largest 100 account for
roughly 94%; this is a link-topology issue, not mostly removable test data.
Files named `testing_api_support` and `test_api_stubs` are still production
dependencies of Chromium component targets and must not be removed by filename.

The packager therefore follows these rules:

- remove only symbols, source maps, generated build helpers, test fonts/data,
  and graphics mock/validation layers known not to be runtime dependencies;
- never remove WebRTC, WebNN, XR, media, ANGLE, or SwiftShader DLLs while GN
  still reports them in the runtime closure;
- treat `full` and `desktop` as part of the distribution identity; capability
  removal must happen in GN first and must be followed by startup and sandbox
  smoke tests;
- keep component and non-component outputs in separate GN directories; their
  C++ runtime and import-library contracts are incompatible.

The release profile implements that explicit bootstrap architecture: the
application package installs the sandbox bootstrap as the business executable.
It reads `runtime_library` from the generated package manifest and loads the
business-named cdylib, such as `playground.dll`. The current verified package is
approximately 268 MiB, including the non-component Framework DLL and runtime data.

## 3. Version compatibility

A release has separate but coordinated versions:

- Framework semantic version and Framework Distribution schema;
- Chromium revision and Tuffite patch-set revision;
- FFI ABI major/minor;
- Shell Protocol major/minor;
- application metadata schema version.

The Framework verifies the callback-table ABI before entering Chromium and
validates application metadata before browser-process startup. ABI-major or
Shell-major mismatches fail with a diagnostic; compatible minor features are
negotiated with table size and, as the API grows, explicit feature bits.

The application lock file records the exact Tuffite runtime distribution used
for reproducible builds. Runtime upgrades are deliberate dependency upgrades,
not silent Framework replacement.

## 4. Chromium build policy

The framework maintains a pinned Chromium revision plus a reviewable Tuffite
patch series. `src/tuffite` is an independent native repository whose `DEPS`
pins Chromium; its `patches/chromium` directory contains ordered
`git format-patch` output. The workspace root commits `.gclient` with the exact
native repository commit, so a second native lock file is unnecessary. Custom
code is concentrated under `src/tuffite/`; upstream-file changes remain minimal
and guarded by generated buildflags. Chromium's existing `root_extra_deps` GN
argument connects `//tuffite:tuffite` to the root graph without patching the root
`BUILD.gn`.

CI verifies both Chromium integration states:

```text
tuffite_in_chromium=true/false
```

With integration disabled, a Ninja graph test proves that Tuffite sources, IDL
bindings, registrations, and behavior hooks are absent. Explorer exposure is
then selected per application through the manifest-backed Blink runtime feature
and enforced again in the browser process.

Chromium rolls should be automated but never blind. The roll pipeline builds all
platforms, runs upstream-relevant tests, applies patch conflict checks, executes
Tuffite integration suites, and produces a compatibility report.

## 5. Crate and npm package layout

Recommended packages:

```text
Rust
  tuffite                    public application API
  tuffite-runtime            Runtime implementation and stable handle types
  tuffite-macros             application and command macros
  tuffite-abi                internal C ABI bindings
  tuffite (build feature)    build integration and binding generation
  tuffite (cli feature)      developer CLI

npm
  tuffite                    renderer runtime, built-in facade, and public types
```

The Rust Shell Protocol codec lives in `tuffite-runtime`; TypeScript parsing and
binding generation live behind the public Rust `tuffite` build feature. The
single npm `tuffite` package owns the browser runtime, built-in TypeScript
contract, generated `window.tuffite` facade, and their public types. A separate
protocol crate is deferred until it has multiple independently versioned
consumers.

The exact public package split should remain small at first. Internal crates can
live in the workspace without being published. Publishing placeholder packages
solely to reserve names is avoided; the first release should contain a minimal
usable API and accurate metadata.

At the time the name was evaluated, the unscoped `tuffite` name appeared
available on both crates.io and npm. Availability is not ownership and must be
rechecked immediately before the first coordinated publication. Trademark and
domain review are separate requirements.

## 6. Platform packaging

### Windows

- signed executable, DLLs, resources, and Chromium subprocess files;
- MSIX or a signed installer according to deployment needs;
- WebView runtimes are not a dependency because Tuffite ships Chromium;
- crash symbols are uploaded separately.

### macOS

- one signed `.app` bundle with correctly nested helper applications;
- hardened runtime entitlements minimized by capability;
- code signing occurs inside-out, followed by notarization and stapling;
- universal binaries or paired architecture artifacts are explicit release
  choices.

### Linux

- AppImage, `.deb`, or another declared target with a documented glibc baseline;
- Chromium sandbox configuration is retained and tested;
- system library assumptions are captured in release CI images.

## 7. Updates

The updater verifies a signed manifest and artifact hashes before activation. It
uses an atomic version directory or platform-native transaction so failure does
not corrupt the currently runnable version. Framework and application artifacts
may be downloaded separately, but activation occurs only for a compatible set.

Rollback retains at least one known-good version. Update metadata includes
minimum supported application schema, Runtime/FFI/Shell versions, platform,
architecture, rollout channel, and expiration or revocation information.

## 8. Security and supply chain

- pinned Chromium, Rust, Node, GN/Ninja, and packaging tool versions;
- dependency lock files committed and reviewed;
- reproducibility metadata and provenance attestations;
- SBOM and third-party licenses per release;
- signed release manifests and protected signing keys;
- Chromium security updates tracked independently of Tuffite feature releases;
- production packages disable development servers, remote debugging, and
  unrestricted DevTools unless explicitly enabled.

## 9. Verification matrix

Each supported platform runs:

- Rust unit, integration, Miri where applicable, and FFI contract tests;
- C++ unit and Chromium browser tests;
- Shell Protocol golden vectors and fuzzing;
- enabled/disabled buildflag graph checks;
- application startup, window, navigation, crash, and shutdown tests;
- `<explorer>` storage, composition, permission, and security tests;
- Network Service proxy, cookie, cache, certificate, policy, SSRF, streaming, and
  cancellation tests;
- packaging install/launch/uninstall and update/rollback tests;
- ASan/UBSan builds where supported and release crash-symbol validation.

Windows `.exe` packaging provisions the NSIS toolchain inside `tuff` on the
first `tuff package --format exe` invocation. NSIS 3.11 and the official archive
SHA-256 are pinned in the CLI; it caches the complete archive and tool directory
under `%LOCALAPPDATA%/Tuffite/tools/nsis-3.11`. Later builds reuse that directory.
Downloads are verified before extraction; extraction is staged and cache updates
are serialized between CLI processes. An interrupted or incomplete extraction
can be repaired from the verified cached archive without another download.
The CLI invokes the cached compiler directly, with its matching `NSISDIR`;
NSIS does not need to be installed globally or supplied by the outer Mise tools.

For CI, cache `%LOCALAPPDATA%/Tuffite/tools`, or set `TUFFITE_TOOLS_CACHE` to a
persistent directory. Set `TUFFITE_TOOLS_OFFLINE=true` to forbid tool downloads;
a cache miss gives an actionable error. `TUFFITE_NSIS_DIR` can instead point at a
complete, explicitly managed NSIS installation for offline or custom setups.
An invalid explicit directory fails without falling back to a download.
This prepares the installer compiler; Windows `.exe` packaging still requires
a Windows host. macOS uses Xcode/OS tools (`xcrun`, `codesign`, `hdiutil`),
managed by Xcode/macOS.
